# MASTER PROMPT — Secure Manager PWA for a Clothing Brand

## 1. Project Objective

Build a complete, production-ready, mobile-first Progressive Web App (PWA) that serves as the mobile version of my existing clothing brand's Manager/Admin dashboard.

The application must preserve the existing brand identity, reuse the current backend and database, synchronize with the existing website and Manager dashboard, enforce secure role-based permissions, and support real mobile push notifications.

This is an extension of the existing system, not a replacement and not a separate application with duplicated data.

**Mandatory first step:** Inspect the actual project before writing code. Identify the framework, application structure, database, API endpoints, authentication system, deployment setup, CSS, design tokens, fonts, logos, existing components, order workflow, inventory logic, QR and serial-code formats, and notification infrastructure.

Do not assume the project uses Firebase, Supabase, or any other particular technology. Detect the actual stack and choose a compatible implementation.

Do not stop after creating a mockup or a plan. Implement the functionality supported by the project, test it, and document any remaining external configuration.

## 22. Real-Time Synchronization — Mandatory Core Feature

Implement true, bidirectional real-time synchronization between the existing website, desktop Manager/Admin dashboard, mobile PWA, backend, database, inventory, and notification center. This is mandatory. The PWA must use the existing authoritative backend and database, not a separate data store.

### 22.1 Real-time data coverage

Synchronize all relevant committed changes supported by the existing schema, including:
- New orders and edits to existing orders.
- Order status transitions, cancellations, delivery attempts, and return operations.
- Product details, prices, images, sizes, and colors.
- Stock quantities, reservations, available stock, and inventory adjustments.
- Low-stock, out-of-stock, and restocked states.
- Notification records, unread counts, and read/unread states.
- Dashboard statistics, sales summaries, charts, and operational activity.
- Authorized changes made by other administrators and staff members.
- Relevant configuration or permission changes affecting the current session.

Example: if an order is marked delivered in the PWA, the website and desktop Manager must reflect the committed change automatically. If stock is updated in the desktop Manager, the PWA must display the new quantity and resulting alerts. Changes must propagate in both directions.

### 22.2 Choose compatible technology

Inspect the current stack and reuse its real-time capabilities where possible. Choose a compatible production-ready mechanism such as WebSockets, Server-Sent Events (SSE), database change streams/subscriptions, database-triggered events, or an event-driven backend/provider.

Do not introduce an unnecessary database, duplicate backend, or incompatible service. If real-time capability does not exist, implement it without breaking the website or desktop Manager.

Do not use frequent full-page refreshes or aggressive polling as a substitute. Polling may be used only as a documented fallback.

### 22.3 Backend is the source of truth

All authoritative changes must be validated and committed by the existing backend:
1. An authorized user submits a change.
2. The backend validates permissions, business rules, and the current record state.
3. The backend commits the change to the authoritative database.
4. A reliable event is published for the committed change.
5. Authorized connected clients receive the event.
6. Relevant screens, counts, lists, and charts update without a full reload.
7. The client confirms final state with the backend when necessary.

Never broadcast an uncommitted change as successful. Frontend events or optimistic UI updates are not proof of a database update.

### 22.4 Reliable event delivery and consistency

Implement:
- Unique event identifiers, event types, resource identifiers, timestamps, and version/sequence information where appropriate.
- Minimal event payloads.
- Server-side authorization for subscriptions and resource access.
- Duplicate-event detection and safe handling of out-of-order events.
- Detection of missed events and resynchronization.
- A transactional outbox or equivalent durable publishing mechanism where appropriate.
- Safe retries and idempotent processing.
- Transactions, version checks, or optimistic concurrency controls where appropriate.
- Protection against silently overwriting newer data.

Do not create duplicate orders, inventory deductions, returns, or notifications when events are retried. Do not allow database commits to be silently separated from event publication where a durable mechanism can prevent it.

### 22.5 Connection and reconnection

Handle Wi-Fi/cellular switching, temporary disconnections, device sleep, browser suspension, and server restarts. Implement:
- Clear Connected, Reconnecting, and Offline indicators.
- Automatic reconnection with exponential backoff and jitter.
- Authentication renewal where applicable.
- Safe subscription restoration.
- Event replay/cursor-based recovery where supported.
- Backend refresh of records changed while disconnected.
- A consistency check when the app returns to the foreground.
- Graceful fallback when the real-time service is unavailable.

Do not lose important changes because a phone was offline. Do not claim a WebSocket remains active while a mobile OS suspends the app. Use active real-time connections while the app is active and Web Push for supported background/closed-app notifications.

### 22.6 Real-time UI

Update only affected components when possible, without reloading the whole app:
- Insert new orders into the correct list.
- Update order status badges and details.
- Update dashboard counters and sales summaries.
- Refresh stock quantities and variant availability.
- Display alerts when stock thresholds are crossed.
- Update notification history and unread counts.
- Reflect edits made by other authorized users.

If another user edits a record while it is being edited locally, detect the conflict, warn the user, preserve unsaved input where possible, and prevent silent overwriting. Show when data may be stale or synchronization is unavailable.

### 22.7 Real-time security

Authenticate every real-time connection. Authorize subscriptions on the server and filter events by role and resource access. Never expose customer records, orders, inventory controls, or admin events to unauthorized users. Do not trust client-supplied roles or resource IDs without server validation. Revoke/disconnect subscriptions after logout, session revocation, or permission changes. Never place PINs, access tokens, or secrets in event payloads or URLs. Apply rate limits and avoid logging sensitive payloads.

### 22.8 Real-time and push are separate

Real-time synchronization updates active interfaces. Push notifications deliver alerts to supported devices when the app is in the background or closed. Implement both systems and coordinate them through backend events. A real-time event is not proof that a phone notification was delivered. Avoid duplicate alerts when one business event triggers both systems.

### 22.9 Real-time acceptance tests

Test the website, desktop Manager, and multiple PWA sessions. Verify:
1. New website orders appear in Manager and PWA without manual refresh.
2. Order status changes from any authorized interface update all relevant connected interfaces.
3. Product and inventory changes propagate in both directions.
4. Dashboard metrics and unread counts update correctly.
5. Disconnected devices catch up after reconnecting.
6. Duplicate and out-of-order events do not corrupt displayed state.
7. Concurrent edits do not silently overwrite newer data.
8. Unauthorized users cannot subscribe to restricted events.
9. Logout/session revocation prevents further protected event access.
10. Real-time failures do not leave records permanently inconsistent.
11. Data remains consistent after reload and across devices.
12. Real-time and push work as separate, coordinated systems.
13. The backend remains the source of truth.

Do not mark synchronization complete until end-to-end propagation, recovery, and authorization tests pass.

## 23. Face ID / Biometric Authentication After First Login

Implement secure biometric authentication for the mobile PWA so users can unlock the app with Face ID, fingerprint, or another supported device authenticator after their first successful login. Availability depends on the device, browser, operating system, and WebAuthn support.

### 23.1 First login and enrollment

On first launch, require the existing authorized login method and role permissions. After successful authentication:
1. Verify the user's identity through the existing backend.
2. Offer the option to enable biometric/passkey login on this device.
3. Explain that biometric verification is handled by the device's authentication system.
4. Register a WebAuthn credential/passkey through a server-verified flow.
5. Associate the credential with the authenticated user and device/account.
6. Confirm successful registration before enabling biometric login.
7. Allow the user to skip setup and continue with the existing login method.

Do not claim biometric login is enabled unless credential registration succeeds.

### 23.2 Subsequent launches

After enrollment, display a branded secure unlock screen on subsequent launches and offer biometric authentication as the primary option. Invoke the supported device authentication prompt through WebAuthn/passkeys. After successful server-side verification, establish or restore a valid backend-authenticated session and route the user to the correct dashboard with the correct role permissions.

Allow the existing authorized login method as a fallback, subject to security policy. Do not require the PIN every time when biometric verification succeeds and a valid session can safely be established. Do not bypass authentication because the app was previously opened, installed, or remembered in local storage.

### 23.3 Technology and platform compatibility

Inspect the existing authentication architecture and integrate with it rather than creating a separate identity system. Use WebAuthn/passkeys with server-side challenge generation and verification wherever supported.

Requirements:
- Generate unpredictable, single-use server challenges.
- Verify the challenge, origin, relying-party ID, credential ownership, and authenticator response on the server.
- Validate credential signatures and required credential data.
- Protect against replay attacks.
- Apply rate limits and monitor repeated failures.
- Use HTTPS and correctly configure the relying-party ID.
- Follow secure WebAuthn implementation standards.

Face ID/fingerprint availability varies. Do not promise every PWA/browser supports every method. Do not build custom camera-based face recognition and do not collect or store facial or fingerprint images. The device/platform handles biometric matching.

### 23.4 Session and role security

Biometric authentication is an additional login method, not a replacement for backend authentication or role-based authorization.

- Establish a valid backend session only after successful server-side verification.
- Apply existing Admin/Staff permissions after authentication.
- Never store passwords, PINs, private authentication keys, or session tokens insecurely in localStorage.
- Use secure HttpOnly, SameSite cookies where compatible.
- Enforce session expiration and revocation.
- Require re-authentication for sensitive actions where policy requires it.
- Require authorized authentication before enrolling a new credential.
